### Выводы по обзору

1. Блокировка на основе lease не гарантирует взаимного исключения при паузе владельца дольше TTL [1–3, 18, 19]; ошибки таймаутов и сетевых разделений повреждают данные в реальных системах [13, 14, 16].
2. Строгое решение – fencing-токены – требует изменения кода [3, 4], а прозрачный lock-delay защищает лишь вероятностно [2]. Проблемы согласованности требуют поддержки на уровне систем управления данными [15, 23], и средства PostgreSQL позволяют проверять запись на стороне СУБД [5, 20–22], но метода их привязки к внешней блокировке нет.
3. TTL выбирают по производительности или эвристикам [1, 8]; адаптивные таймауты по распределению задержек [7] для блокировок с ограничением риска ε не применялись.
4. Lockset-анализ [10, 24], анализ истории операций [11, 12], LLM с проверкой результатов [17] и верификация в TLA+ [6, 25] пригодны для вывода соответствия «блокировка – данные» и проверки модели.

Нерешёнными остаются строгая защита без изменения кода и выбор TTL по допустимому риску.

## 3. Обзор и сравнение аналогов

### Прямые аналоги

1. **Ручной fencing-токен – Redisson, Hazelcast FencedLock** (https://redisson.pro/docs/data-and-services/locks-and-synchronizers/, https://docs.hazelcast.com/hazelcast/latest/data-structures/fencedlock). Блокировка выдаёт монотонный токен, хранилище отклоняет записи со старым токеном. Ограничения: токен и проверку добавляют в код каждой записи.
2. **Lock-delay – Chubby, Consul** (https://developer.hashicorp.com/consul/docs/automate/session). После потери владельца блокировка некоторое время не выдаётся. Ограничения: защита вероятностная, растёт простой ресурса.
3. **Сторожевые процессы продления – watchdog Redisson, KeepAlive в etcd** (https://etcd.io/docs/v3.5/learning/api/). Фоновый поток продлевает блокировку. Ограничения: пауза процесса останавливает и сторожевой поток, интервал фиксирован.
4. **Advisory locks PostgreSQL** (https://www.postgresql.org/docs/18/explicit-locking.html). Блокировка внутри СУБД снимается вместе с транзакцией. Ограничения: нужна замена блокировки в коде, защищена только одна СУБД, сессионные блокировки несовместимы с пулом в режиме транзакций.

### Косвенные аналоги

1. **Прокси с подстановкой контекста – pgvpd** (https://docs.rs/crate/pgvpd/latest). Прокси выставляет сессионные переменные, политики RLS в СУБД проверяют доступ. Ограничения: контекст статичен, эпохи блокировок не поддерживаются.
2. **Адаптивные таймауты – φ accrual, RFC 6298** (https://www.rfc-editor.org/rfc/rfc6298). Таймаут вычисляется по наблюдаемым задержкам. Ограничения: решают задачу обнаружения отказов, а не выбора TTL блокировки.
3. **Аудит – pgAudit, S3 Object Lock** (https://github.com/pgaudit/pgaudit, https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html). Журнал операций и неизменяемое хранение. Ограничения: журнал не связан с эпохами владения, слепков перед критической секцией нет.
4. **Проверка и анализ – Jepsen/Elle, Eraser** (https://github.com/jepsen-io/elle). Поиск аномалий по истории операций. Ограничения: инструменты тестирования, а не защита работающей системы.

### Выводы по сравнению

Ни одно решение не сочетает строгую защиту с отсутствием изменений кода, и все используют фиксированный TTL. Из аналогов берутся fencing-токены, схема «прокси подставляет контекст – СУБД проверяет» из pgvpd, advisory locks как альтернативный уровень защиты, φ accrual и RFC 6298 как базовые линии для модели TTL. Устраняются необходимость изменения кода, ручная настройка защищаемых данных и эмпирический выбор TTL. Сохраняется ограничение: повторный захват блокировки другим потоком того же экземпляра при общем пуле соединений не различим.

## 4. Итоги

**Итоговая тема ВКР:** Разработка прототипа компонента защиты целостности данных при распределённых блокировках средствами PostgreSQL и адаптивной модели таймаутов

**УДК для тезиса:** 004.75

**Ключевые слова:** распределённые блокировки, целостность данных, lease, fencing-токен, PostgreSQL, advisory locks, адаптивный таймаут, вероятностная модель, TLA+.

### Актуальность исследования

Распределённые блокировки защищают критические операции бэкенд-систем: списания, бронирование, резервирование. При паузе владельца дольше TTL блокировка переходит другому процессу, и запись проснувшегося владельца молча нарушает целостность данных [1, 3, 18]. Такие ошибки подтверждены в реальных системах [13, 14, 16]. Строгая защита fencing-токенами требует переписывания кода [3, 4], прозрачный lock-delay нестрог [2], хотя PostgreSQL позволяет проверять легитимность записи на своей стороне [20, 22]. TTL выбирают эмпирически [1, 14], а рост хвостовых задержек [9], в том числе из-за обращений к LLM в критических секциях, делает фиксированный TTL ненадёжным. Поэтому нужен компонент, который строго защищает данные без изменения кода и выбирает TTL по допустимому риску.

### Цель исследования

Разработка и экспериментальная оценка прототипа компонента, защищающего целостность данных при распределённых блокировках без изменения кода приложения в формально определённых условиях применимости, и вероятностной модели динамического расчёта срока действия блокировки.

### Задачи исследования

1. Провести обзор подходов к распределённым блокировкам и методов защиты от истечения lease, систематизировать их по инвазивности, накладным расходам и гарантиям.
2. Разработать формальную модель блокировки с прозрачной защитой, условия её эквивалентности ручному fencing-токену и проверить свойство безопасности в TLA+.
3. Разработать архитектуру прокси-компонента, перехватывающего обращения к Redis и SQL-запросы.
4. Разработать методы отслеживания эпох владения по трафику и вывода соответствия «ключ блокировки – данные» с уточнением офлайн-модулем на основе LLM.
5. Реализовать привязку блокировки к транзакции PostgreSQL: скрытые fencing-токены в триггерах, advisory locks, проверка перед коммитом с откатом транзакции.
6. Разработать схему журнала аудита и слепков состояний в S3-совместимом хранилище для восстановления после частичного сбоя.
7. Собрать телеметрию пауз, времени критических операций и конфликтов блокировок на стенде.
8. Разработать вероятностную модель TTL, ограничивающую вероятность преждевременного истечения порогом ε при минимальном простое.
9. Реализовать прототип компонента как сервис-адаптер для протоколов Redis и PostgreSQL.
10. Экспериментально сравнить решение с блокировкой без защиты и с ручным fencing-токеном: накладные расходы, отсутствие нарушений целостности, поведение на границах применимости.
11. Сформулировать рекомендации по внедрению метода.

### Датасеты и сервисы

Открытых датасетов с нарушениями взаимного исключения и паузами владельцев нет, поэтому данные создаются в работе:

- **Синтетический бенчмарк** – демо-сервисы (списание, резервирование, заказ) на Redisson и redsync с известным соответствием «блокировка – данные»; будет опубликован в открытом репозитории.
- **Телеметрия пауз** – распределения пауз и времени критических секций, собранные на стенде с внесением отказов; нужны для модели TTL.
- **Сервисы стенда:** Redis (https://redis.io), PostgreSQL (https://www.postgresql.org), MinIO (https://min.io), Toxiproxy (https://github.com/Shopify/toxiproxy), Prometheus (https://prometheus.io), TLA+ (https://lamport.azurewebsites.net/tla/tla.html), Ollama (https://ollama.com).
